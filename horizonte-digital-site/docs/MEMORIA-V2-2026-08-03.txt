- cronômetro;
- pontuação;
- progressão;
- salvamento;
- trânsito limitado;
- menus;

11. RECONCILIAÇÃO: HORIZONTE ENGINE FRAMEWORK E AEROWORLD CORE
======================================================================

Existem duas ideias técnicas relacionadas, mas diferentes:

A. Horizonte Engine Framework

- camada reutilizável inicialmente sobre Unreal Engine 5.8;
- criada a partir de sistemas comprovados nos jogos;
- ajuda a padronizar e acelerar projetos da Horizonte Digital.

B. AeroWorld Core

- núcleo de simulação e regras do AeroWorld;
- deve permanecer independente da Unreal Engine;
- deve poder compilar e testar sem depender do runtime visual da Unreal;
- conversa com a Unreal por um adaptador;
- pode concentrar física de voo, simulação, carreira, save, IA,
  validação, contratos e sincronização.

Essas ideias não precisam se contradizer:

- a Unreal pode cuidar da apresentação, editor e runtime visual;
- o Framework pode padronizar a integração e sistemas comuns;
- o AeroWorld Core pode manter a lógica crítica independente.

Não fundir tudo em um único bloco sem uma decisão arquitetural aprovada.

14. HORIZONTE IA
======================================================================

NOME

Horizonte IA, também referida em alguns documentos como Horizonte AI.

OBJETIVO GERAL

Criar uma inteligência artificial e um ambiente de criação que ajudem o
usuário a:

- programar;
- analisar;
- escrever;
- planejar;
- criar projetos;
- importar arquivos;
- editar arquivos;
- organizar código;
- revisar;
- depurar;
- gerar documentação;
- trabalhar no celular, tablet e computador;
- manter contexto de projetos;
- preparar alterações mesmo quando ferramentas pesadas não puderem rodar.

A Horizonte IA deve ser útil mesmo sem computador para tarefas que o
dispositivo suportar.

ESTÚDIO MOBILE JÁ DISCUTIDO

Foi planejada/publicada uma experiência de Estúdio Mobile capaz de:

- criar projetos;
- importar projetos;
- editar arquivos;
- renomear arquivos;
- excluir arquivos;
- visualizar arquivos;
- salvar projetos;
- confirmar alterações;
- baixar projeto em ZIP;
- guardar dados no navegador quando aplicável.

Não afirmar que isso substitui uma IDE completa sem testes.
Não afirmar que consegue compilar qualquer projeto.
Não afirmar que executa Unreal ou Blender no celular.

LIMITES DE PROCESSAMENTO

Foi aceito que a Horizonte IA não precisa executar projetos pesados de
Unreal Engine ou Blender sem computador.

Ela pode, conforme o ambiente:

- ler arquivos;
- editar texto;
- editar código;
- criar estrutura de pastas;
- preparar scripts;
- analisar logs;
- criar documentação;
- montar patches;
- organizar assets por metadados;
- preparar arquivos para posterior execução;
- gerar ZIP;
- explicar passos;
- sincronizar trabalho.

Ela não deve fingir que renderizou, compilou, abriu a Unreal ou executou
Blender quando isso não ocorreu de verdade.

ANDROID

Foi discutida uma versão Horizonte IA Android 1.1 com comportamento de
continuação de resposta quando outro aplicativo está aberto, usando
serviço em primeiro plano e notificação.

Regra de comportamento:

- a tarefa pode continuar enquanto o serviço estiver ativo;
- a notificação deve informar o processamento;
- quando terminar, o serviço pode ser encerrado;
- se o aplicativo for forçado a fechar, o processamento pode ser
  interrompido;
- não prometer execução ilimitada em segundo plano;
- respeitar limitações do Android e políticas atuais.

IPHONE E ANDROID

Preferência registrada:

- no iPhone, usar programação e raciocínio mais leves;
- no Android, permitir mais contexto de arquivos, respostas de código
  maiores e alterações mais completas quando o hardware permitir.

Hierarquia conceitual registrada:

1. computador com placa de vídeo dedicada;
2. computador com vídeo integrado;
3. Android;
4. iPhone.

Essa hierarquia não é absoluta para toda tarefa. Verifique memória, CPU,
armazenamento, limites do sistema, modelo disponível e tamanho dos
arquivos antes de decidir.

Não inventar benchmark.
Não afirmar capacidade sem teste.

PRINCÍPIOS DA HORIZONTE IA

- preservar o que funciona;
- melhorar somente o que precisa;
- entregar código funcional quando solicitado;
- evitar pseudocódigo quando o usuário pediu implementação real;
- escolher ferramentas compatíveis com o ambiente;
- nunca declarar sucesso sem validação;
- indicar limitações;
- manter arquivos recuperáveis;
- criar backup antes de alterações importantes;
- não apagar sem autorização;
- registrar mudanças;
- priorizar qualidade e clareza;
- evitar dependência desnecessária de serviços externos;
- proteger dados privados;
- não compartilhar credenciais;
- permitir evolução modular;
- manter o usuário no controle.

# AeroWorld - Architecture Overview

## Summary

AeroWorld uses a hybrid architecture:

- Unreal Engine 5 is recommended for presentation, editor tooling and visual runtime.
- AeroWorld Core remains independent and owns simulation, flight dynamics, save, career, AI orchestration, cloud sync, validation and public contracts.

## Core Boundary

```mermaid
flowchart LR
    UE5[UE5 Presentation]
    Adapter[UE5 Adapter]
    Core[AeroWorld Core]
    Cloud[Horizonte Cloud]

    UE5 <--> Adapter
    Adapter <--> Core
    Core <--> Cloud
```

## Key Rules

- Core must compile and run without UE5.
- Structural changes require ADR.
- Save must work offline.
- Cloud sync must not block flight.
- Creator content must pass validation.
- Marketplace packages must be signed.

- `docs/04-architecture-document.md`

# AeroWorld - Game Design Document

## 1. Visao

AeroWorld sera uma plataforma mundial de aviacao civil, nao apenas um jogo. O produto deve permitir voar, aprender, criar, explorar e compartilhar experiencias aeronauticas com alto nivel de realismo, acessibilidade progressiva e suporte de IA.

## 2. Pilares de design

1. **Realismo escalavel:** o jogador iniciante deve conseguir aprender com apoio, enquanto pilotos experientes devem encontrar sistemas profundos.
2. **Mundo vivo:** aeroportos, clima, trafego, passageiros, servicos de solo e economia devem reagir de forma crivel.
3. **Plataforma aberta:** criadores devem produzir aeronaves, missoes, aeroportos, cidades, objetos e pinturas dentro de regras tecnicas e de qualidade.
4. **Continuidade:** offline, online e modo hibrido devem manter progresso, carreira e conteudo de forma resiliente.
5. **Civil primeiro:** primeiras versoes focam aviacao civil. Aeronaves militares ficam fora do escopo inicial.

## 3. Escopo de aeronaves civis

- Avioes civis leves.
- Helicopteros civis.
- Jatos executivos.
- Turboelices.
- Avioes agricolas.
- Planadores.
- Hidroavioes.

## 4. Modos principais

### 4.1 Free Flight

Modo livre para escolher aeronave, local, clima, horario, carga, passageiros e regras de assistencia.

### 4.2 Career

Progressao persistente com horas de voo, licencas, reputacao, empresas, missoes, contratos, manutencao, historico financeiro e conquistas.

### 4.3 Training

Treinamento modular com instrutor IA, explicacao dos instrumentos, avaliacao de manobras, checklists e aulas por tipo de aeronave.

### 4.4 Missions

Missoes manuais e geradas por IA: transporte executivo, turismo, carga regional, resgate civil, taxi aereo, pulverizacao agricola, voos panoramicos, treinamento, operacoes em hidroaviao e planador.

### 4.5 Online World

Mundo compartilhado com trafego de jogadores, ATC humano ou IA, eventos, empresas, marketplace, comunidades e conteudo aprovado.

### 4.6 Hybrid Mode

O modo hibrido e obrigatorio: se a internet cair, o jogo continua localmente. Ao reconectar, o sistema sincroniza progresso, inventario, horas de voo, missoes, fotos, replays e configuracoes com resolucao de conflitos.

- Mecanicos.
- Passageiros.
- Trafego aereo.

- Gerador de missoes.
- Sistema de ajuda contextual.
- Piloto automatico assistido por IA quando solicitado.

| Video pre-renderizado | Qualidade alta | Pouca flexibilidade, tamanho maior | Bom para trailer |
| Render em tempo real UE5 | Integrado e adaptavel | Exige performance minima | Recomendado para jogo |
| Splash estatica | Simples | Pouco impacto de marca | Usar como fallback |

## 12. Criterios de aceitacao

- Pode ser pulada.
- Nao passa de 5 segundos por padrao.
- Possui fallback estatico.
- Audio respeita volume global.
- Nao bloqueia logs de inicializacao.

## 13. Roadmap

- Fase 1.1: design textual.
- Fase 2: animatic.
- Fase 3: implementacao no launcher.
- Fase 4: integracao com jogo.

## 14. Riscos

- Splash longa irritar usuario.
- Cinematica pesar em hardware baixo.
- Marca competir com carregamento real.

## 15. Integracao

Integra Brand Book, Visual Bible, Audio Bible, UI/UX Bible, Launcher e Development Pipeline.

# AeroWorld - Technical Design Document

## 1. Objetivo tecnico

Construir uma plataforma de simulacao de aviacao civil modular, escalavel, preparada para muitos anos de desenvolvimento, equipes grandes, mundo global com streaming e sistemas extensos de IA, fisica, clima, rede, cloud, criacao de conteudo e marketplace.

## 2. Principios

- Arquitetura limpa.
- SOLID.
- Separacao entre simulacao, renderizacao, rede, persistencia e ferramentas.
- Modulos independentes com contratos explicitos.
- ECS onde houver grande volume de entidades dinamicas.
- Multithreading desde a base.
- Streaming assincrono.
- GPU compute para cargas adequadas.
- Baixo consumo de memoria.
- Preparacao para DirectX 12, Vulkan, VR e multiplos monitores.

## 3. Linguagens candidatas

| Alternativa | Vantagens | Desvantagens | Recomendacao |
|---|---|---|---|
| C++ moderno | Performance, ecossistema de engines, acesso baixo nivel, DirectX/Vulkan, compatibilidade com Unreal | Complexidade alta, risco de bugs de memoria, build pesado | Recomendado para runtime/engine |
| Rust | Seguranca de memoria, concorrencia forte, bom para servicos e ferramentas | Ecossistema de engine menor, integracao com middleware AAA mais trabalhosa | Bom para servicos, ferramentas e cloud |
| C# | Produtividade, bom para ferramentas editoriais | Menos adequado para engine AAA propria de baixo nivel | Bom para ferramentas internas |
| TypeScript | Excelente para web, launcher, paineis e servicos frontend | Nao adequado para simulacao central | Usar apenas em interfaces web |

**Status:** pendente de aprovacao.

## 4. Modelo de execucao

O runtime deve ser dividido em dominios:

- Main/game orchestration thread.
- Render thread.
- Physics/simulation thread.
- Flight dynamics workers.
- Terrain streaming workers.
- Asset IO workers.
- Network replication thread.
- Audio thread.
- AI jobs.
- Telemetry/logging jobs.

O sistema de jobs deve permitir prioridade, cancelamento, afinidade e medicao de tempo.

## 5. Persistencia local e nuvem

O jogo deve manter um banco local resiliente para modo offline/hibrido e sincronizar com cloud quando possivel.

| Alternativa | Vantagens | Desvantagens | Recomendacao |
|---|---|---|---|
| SQLite local + cloud event log | Robusto, auditavel, bom offline, simples de debugar | Exige desenho cuidadoso de conflitos | Recomendado |
| Arquivos JSON locais | Simples no inicio | Fraco para escala, corrupcao e sincronizacao | Apenas prototipos |
| Banco embutido NoSQL | Flexivel | Dependencia maior, mais dificil auditar | Avaliar depois |

**Status:** pendente de aprovacao.

## 6. Rede

O online deve separar:

- Autenticacao.
- Perfil e conta.
- Sincronizacao de carreira.
- Mundo online.
- Presenca de jogadores.
- Trafego multiplayer.
- Chat/voz futuro.
- Marketplace.
- Moderacao.

Multiplayer de simulador nao precisa replicar cada detalhe interno da aeronave; deve replicar estado externo, intencoes, eventos importantes e interpolacao visual.

## 7. IA

A IA deve ser modular:

- IA local para copiloto, instrutor e ajuda contextual.
- IA de simulacao para trafego, passageiros e mecanicos.
- IA server-side para geracao de missoes, moderacao e analise de conteudo.
- IA opcional em nuvem para dialogo, explicacoes e planejamento.

Decisao critica futura: quais funcoes de IA podem rodar offline e quais dependem de cloud.

## 8. Dados reais do mundo

O sistema deve aceitar multiplas fontes:

- Elevacao.
- Imagens/satelite/licenciadas.
- Vetores geograficos.
- Aeroportos.
- Navegacao.
- Estradas.
- Rios.
- Clima.
- Trafego.

Toda fonte de dados precisa de licenca rastreavel, versao, cache, pipeline de ingestao e camada de correcao manual.

## 9. Observabilidade

Desde o inicio, o projeto deve registrar:

- FPS e frame time.
- Uso de CPU por thread.
- Uso de GPU.
- Memoria por subsistema.
- Latencia de streaming.
- Latencia de rede.
- Erros de sincronizacao.
- Determinismo da simulacao.
- Crash dumps.
- Eventos de carreira.

# AeroWorld - Engine Design Document

## 1. Decisao central: engine propria, Unreal Engine 5 ou hibrida

Esta e uma decisao estrutural. Nenhuma implementacao deve comecar antes de aprovacao.

Referencias oficiais consultadas:

- Unreal Engine FAQ: https://www.unrealengine.com/faq
- Unreal Engine EULA: https://www.unrealengine.com/eula/unreal
- Unreal Engine World Partition: https://dev.epicgames.com/documentation/en-us/unreal-engine/world-partition-in-unreal-engine

Observacao: termos comerciais e licencas podem mudar. Antes de aprovacao final, deve haver revisao juridica e tecnica atualizada.

## 2. Alternativa A - Engine propria completa

Criar toda a engine AeroWorld do zero: renderer, editor, streaming, fisica, ferramentas, importadores, rede, audio, assets, build pipeline e runtime.

### Vantagens

- Controle total da arquitetura.
- Sem dependencia estrategica de fornecedor externo.
- Otimizacao extrema para simulacao planetaria.
- Licenciamento mais controlavel no longo prazo.
- Melhor liberdade para marketplace, criador de conteudo e pipelines proprietarios.

### Desvantagens

- Custo inicial muito alto.
- Demora de anos ate paridade visual e ferramental com engines AAA.
- Exige equipe grande e muito experiente desde o inicio.
- Alto risco tecnico em rendering, editor, streaming global, VR e multiplataforma.
- Menos tempo para gameplay, aeronaves e comunidade nos primeiros anos.

### Como seria construida

1. **Core Platform:** memoria, jobs, ECS, reflection, serialization, plugin loader, telemetry.
2. **Rendering Backend:** abstracao RHI para DirectX 12 e Vulkan.
3. **Renderer:** PBR, sombras, atmosfera, nuvens, agua, terrain, vegetation, temporal upscaling, VR.
4. **World/Terrain:** globo, tiles, LOD, reprojecao geografica, cache, streaming assincrono.
5. **Physics:** integracao de rigid body, colisao, constraints e solver customizado para aeronaves.
6. **Flight Dynamics:** aerodinamica, motores, combustivel, sistemas eletricos/hidraulicos.
7. **Editor:** scene editing, airport tools, mission tools, aircraft tools, validation.
8. **Asset Pipeline:** importacao, compressao, cook, versionamento, dependencias.
9. **Networking/Cloud:** contas, sync, multiplayer, marketplace, moderacao.
10. **SDK:** documentacao, exemplos, API de mods, validadores e empacotamento.

## 3. Alternativa B - Unreal Engine 5 como base

Usar UE5 para renderizacao, editor, assets, input, audio, plataforma, tooling e parte do streaming, criando os sistemas especificos do AeroWorld como modulos proprietarios.

### Vantagens

- Base AAA madura.
- Editor poderoso desde o primeiro dia.
- C++ e acesso a codigo-fonte sob EULA.
- Ecossistema grande de artistas e programadores.
- Recursos prontos para mundo aberto, rendering moderno, audio, input, animacao e tooling.
- Ajuda a chegar mais rapido a uma demo visual convincente.

### Desvantagens

- Dependencia de licenca e roadmap da Epic.
- Customizacoes profundas podem dificultar upgrades.
- World Partition nao resolve sozinho escala planetaria.
- Simulacao deterministica e streaming geografico global exigem sistemas proprios.
- Distribuicao de ferramentas/modding precisa respeitar restricoes da EULA.
- Performance de simulador pode exigir contornar partes genericas da engine.

## 4. Alternativa C - Estrategia hibrida recomendada

Usar UE5 como camada de apresentacao, editor e runtime inicial, enquanto o nucleo AeroWorld fica isolado em bibliotecas proprietarias independentes: simulacao, flight dynamics, cloud sync, missao, carreira, dados do mundo, streaming geografico e SDK.

### Vantagens

- Reduz risco inicial.
- Permite prototipos e demos mais cedo.
- Mantem propriedade intelectual nos sistemas centrais.
- Abre caminho para migrar parte do renderer/runtime no futuro se necessario.
- Equilibra velocidade, qualidade visual e independencia tecnica.

### Desvantagens

- Exige disciplina forte para evitar acoplamento excessivo ao UE5.
- Duas arquiteturas precisam conversar bem.
- Parte do pipeline ficara condicionada a Unreal.
- Requer camada de abstracao desde o inicio.

### Recomendacao tecnica

**Recomendo a Alternativa C: estrategia hibrida com UE5 como base visual/editorial e AeroWorld Core independente.**

Motivo: competir com Microsoft Flight Simulator e X-Plane exige muitos anos, mas tambem exige tracao visual e ferramental cedo. Uma engine propria completa desde o dia 1 aumenta demais o risco. A estrategia hibrida permite construir o diferencial real do AeroWorld em sistemas proprios, sem desperdiÃƒÂ§ar anos recriando ferramentas genericas de engine.

**Status:** pendente de aprovacao do proprietario.

## 5. Fronteiras obrigatorias do AeroWorld Core

Mesmo usando UE5, estes modulos nao devem depender diretamente de Unreal:

- Flight Dynamics Engine.
- Aircraft Systems.
- Career Engine.
- Mission Engine.
- Cloud Sync.
- Save System.
- World Data Model.
- AI Orchestration.
- Content Validation.
- Marketplace backend.

UE5 deve consumir esses sistemas por adapters.

## 6. Preparacao para engine propria futura

Se a estrategia hibrida for aprovada, a arquitetura deve manter:

- Abstracao de renderer-facing data.
- Formatos de mundo proprios.
- Simulacao independente de frame rate.
- Serializacao proprietaria versionada.
- Testes headless sem UE.
- Servicos cloud independentes.
- SDK documentado sem expor dependencia desnecessaria do UE.

# AeroWorld - Architecture Document

## 1. Visao arquitetural

AeroWorld deve ser composto por modulos independentes ligados por contratos estaveis. Cada modulo deve poder evoluir, ser testado e ser substituido com impacto controlado.

## 2. Camadas

```mermaid
flowchart TD
    UI[Presentation / UI / VR / Multi-monitor]
    Runtime[Runtime Orchestration]
    Sim[Simulation Core]
    World[World and Streaming]
    Services[Online and Cloud Services]
    Tools[Creator and Studio Tools]
    Data[Data, Assets and Persistence]

    UI --> Runtime
    Runtime --> Sim
    Runtime --> World
    Runtime --> Services
    Tools --> Data
    World --> Data
    Sim --> Data
    Services --> Data
```

## 3. Modulos principais

### Rendering Engine

Responsavel por apresentar mundo, aeronaves, atmosfera, agua, nuvens, terreno, cidades, aeroportos, cockpit, VR e multiplos monitores. Se UE5 for aprovado, este modulo comeca como adapter sobre UE5.

### Physics Engine

Responsavel por colisao, rigid bodies, constraints, contato com solo, rodas, flutuacao de hidroavioes, interacao com vento e objetos.

### Flight Dynamics Engine

Responsavel pela aerodinamica, sustentacao, arrasto, estabilidade, superficies de controle, motores, helice, turbina, rotor, planador, hidroaviao e aeronaves agricolas.

### Weather Engine

Clima global, METAR/TAF quando disponivel, nuvens, vento, turbulencia, chuva, gelo, termicas, visibilidade e transicoes.

### Terrain Engine

Representacao do planeta, elevacao, tiles, LOD, materiais, rios, estradas, vegetacao, cidades e correcao manual.

### Streaming Engine

Carregamento assincrono de mundo, terreno, aeroportos, objetos, texturas, trafego, clima e dados online.

### AI Engine

Orquestra copiloto, instrutor, ATC, passageiros, mecanicos, trafego, ajuda contextual e geracao de missoes.

### Cloud Engine

Conta, progresso, sync hibrido, armazenamento de fotos/replays, configuracoes, conquistas e integridade.

### Networking Engine

Presenca, multiplayer, trafego online, eventos, estado externo de aeronaves, voz/chat futuro e tolerancia a latencia.

### Mission Engine

Missoes manuais e geradas por IA, objetivos, avaliacao, recompensas, falhas, briefing/debriefing e telemetria.

### Career Engine

Licencas, empresas, contratos, reputacao, frota, manutencao, financas, historico e conquistas.

### Aircraft Systems

Eletrica, hidraulica, combustivel, pressurizacao, trem de pouso, portas, carga, falhas, desgaste e manutencao.

### Avionics

Instrumentos analogicos, glass cockpit, GPS, FMS, radio, transponder, autopilot, mapas e alertas.

### Audio Engine

Motores, vento, cockpit, radio, ambiente, passageiros, alertas, spatial audio e VR.

### Input Engine

Joystick, yoke, throttle, pedais, teclado, mouse, gamepad, touch futuro e perfis por aeronave.

### Mod Engine

SDK, empacotamento, permissao, sandbox, APIs, validacao e compatibilidade.

### Marketplace

Submissao, revisao, aprovacao, distribuicao, atualizacoes, licencas, ranking, moderacao e pagamentos futuros.

### Creator Engine

Ferramentas para aeronaves, aeroportos, missoes, pinturas, cidades, objetos e validacao local.

### Save System

Persistencia local, snapshots, event log, cloud sync, resolucao de conflitos e versao de dados.

### Plugin System

Extensoes carregaveis com permissao, versionamento, sandbox, manifestos, dependencias e testes de compatibilidade.

## 4. Independencia de modulos

Cada modulo deve expor:

- Interface publica.
- Eventos de entrada e saida.
- Formato de dados versionado.
- Testes automaticos.
- Medidas de performance.
- Politica de falha.
- Dono tecnico.

## 5. ECS

ECS deve ser usado para:

- Trafego aereo.
- Objetos do mundo.
- Veiculos de solo.
- Passageiros simulados.
- Efeitos ambientais.
- Sistemas com milhares de entidades simples.

ECS nao deve ser imposto a todos os dominios. Flight dynamics e avionics podem usar modelos orientados a dominio quando isso for mais claro e testavel.

## 6. Contratos de sincronizacao hibrida

O sistema deve operar com:

- Estado local autoritativo temporario quando offline.
- Event log para acoes de carreira e progresso.
- Versoes e timestamps assinados.
- Resolucao deterministica de conflitos.
- Reenvio idempotente.
- Auditoria de integridade para evitar fraude.

## 7. Decisoes pendentes

- Engine base: propria, UE5 ou hibrida.
- Linguagem principal do core.
- Provedor cloud.
- Banco local.
- Formato de assets.
- Politica de modding.
- Nivel de IA offline na primeira versao.

# AeroWorld - Digital Twin Design Document

## 1. Objetivo

O Digital Twin do AeroWorld sera a camada que representa o mundo real dentro da plataforma: planeta, aeroportos, cidades, relevo, rios, estradas, clima, trafego, dados aeronauticos e objetos civis. Ele nao deve ser apenas um cenario visual; deve ser uma representacao versionada, rastreavel e atualizavel do mundo.

## 2. Principios

- Usar dados reais sempre que licenca, qualidade e custo permitirem.
- Separar dado bruto, dado processado e dado corrigido manualmente.
- Manter versao e origem de cada fonte.
- Permitir streaming por regiao, nivel de detalhe e prioridade de voo.
- Funcionar em modo offline com cache local.
- Permitir correcao manual por equipe interna e criadores aprovados.
- Integrar com UE5 por adapters, sem prender o modelo de dados ao UE5.

## 3. Camadas do Digital Twin

1. **Geospatial Base:** coordenadas, projecoes, elevacao, malha do planeta e tiles.
2. **Natural World:** agua, rios, costa, vegetacao, relevo e biomas.
3. **Built World:** cidades, estradas, predios, pontes, aeroportos, portos e objetos.
4. **Aviation Layer:** pistas, taxiways, gates, frequencias, navaids, procedimentos, espacos aereos.
5. **Dynamic Layer:** clima, trafego, eventos, obras, NOTAM futuro e atividade online.
6. **Correction Layer:** ajustes manuais, melhorias de criadores, overrides oficiais.

## 4. Fontes de dados candidatas

| Alternativa | Vantagens | Desvantagens | Recomendacao |
|---|---|---|---|
| Dados abertos | Custo menor, boa cobertura, comunidade ativa | Qualidade irregular, licencas variadas | Usar quando licenca permitir |
| Dados comerciais | Maior qualidade e suporte | Custo alto, restricoes legais | Avaliar por regiao critica |
| Conteudo gerado por IA | Preenche lacunas e acelera producao | Pode errar, exige revisao e validacao | Usar como assistente, nao como fonte autoritativa |
| Criadores aprovados | Escala com comunidade | Exige ferramentas e moderacao | Usar com certificacao tecnica |

**Status:** pendente de aprovacao por fonte e por licenca.

## 5. Pipeline de ingestao

1. Receber dado bruto.
2. Registrar origem, licenca, data e versao.
3. Normalizar coordenadas e unidades.
4. Validar consistencia geometrica.
5. Gerar tiles e LODs.
6. Rodar validadores automaticos.
7. Aplicar correcoes manuais aprovadas.
8. Publicar pacote versionado.
9. Replicar para CDN/cache.
10. Registrar telemetria de qualidade em uso real.

## 6. Streaming do Digital Twin

O Streaming Engine deve solicitar dados por:

- Posicao da aeronave.
- Velocidade e altitude.
- Rota planejada.
- Proximidade de aeroportos.
- Qualidade grafica configurada.
- Cache disponivel.
- Estado online/offline.

## 7. Contratos com outros modulos

- **Terrain Engine:** consome elevacao, materiais, agua e LODs.
- **Rendering Engine:** consome representacoes visuais prontas para o adapter UE5.
- **Weather Engine:** consome geografia, relevo e regioes climaticas.
- **Flight Dynamics Engine:** consome altitude do solo, vento local e superficies.
- **AI Engine:** consome aeroportos, rotas, trafego e pontos de interesse.
- **Mission Engine:** consome locais, aeroportos, regioes e eventos.
- **Creator Engine:** produz correcoes e conteudo candidato.

## 8. Regras de qualidade

- Nenhum dado sem licenca clara entra no build oficial.
- Toda correcao manual precisa ser rastreavel.
- Aeroportos oficiais exigem validacao mais rigorosa que objetos comuns.
- O sistema deve degradar qualidade visual antes de travar simulacao.
- O cache local deve preservar areas usadas recentemente.

## 9. Riscos

- Licenciamento global pode ser caro.
- Dados reais podem estar desatualizados.
- Cobertura mundial completa exige muitos anos.
- Streaming planetario exige infraestrutura robusta.
- Conteudo de criadores exige moderacao e padrao tecnico.

# AeroWorld - Flight Dynamics Bible

## 1. Objetivo

A Flight Dynamics Bible define os principios da simulacao de voo do AeroWorld. Este documento orienta aeronaves civis, helicopteros, jatos executivos, turboelices, avioes agricolas, planadores e hidroavioes.

## 2. Filosofia

O modelo deve ser fisicamente crivel, testavel, extensivel e configuravel por tipo de aeronave. Realismo nao deve depender de truques visuais; controles, resposta aerodinamica, motores, peso, vento e falhas devem nascer de um modelo de simulacao consistente.

## 3. Requisitos centrais

- Simulacao independente do frame rate.
- Taxa fixa de simulacao.
- Unidades padronizadas.
- Telemetria completa.
- Reprodutibilidade para testes.
- Separacao entre modelo fisico, visual e input.
- Suporte a falhas e desgaste.
- Adaptacao por tipo de aeronave.

## 4. Alternativas de modelo aerodinamico

| Alternativa | Vantagens | Desvantagens | Recomendacao |
|---|---|---|---|
| Tabelas de performance | Rapido, previsivel, bom para prototipos | Menos emergente, pode parecer artificial | Usar em prototipo inicial |
| Blade element / superficies | Mais fisico, extensivel, bom para diferentes aeronaves | Mais complexo e caro em CPU | Caminho recomendado para core |
| CFD em tempo real | Muito detalhado teoricamente | Custo alto, inviavel como base geral | Nao recomendado para runtime geral |
| Modelo hibrido | Equilibra performance e realismo | Exige calibracao cuidadosa | Recomendado a medio prazo |

**Status:** pendente de aprovacao tecnica.

## 5. Dominios de simulacao

### Aerodinamica

- Sustentacao.
- Arrasto.
- Momento.
- Estol.
- Flaps.
- Spoilers.
- Superficies de controle.
- Efeito solo.
- Turbulencia.
- Gelo.

### Propulsao

- Motor a pistao.
- Turboelice.
- Jato executivo.
- Helicoptero.
- Planador sem motor.
- Sistemas agricolas com carga variavel.

### Massa e balanceamento

- Combustivel.
- Passageiros.
- Carga.
- Centro de gravidade.
- Pulverizacao agricola consumindo carga.
- Flutuadores em hidroavioes.

### Superficie e contato

- Pneus.
- Trem de pouso.
- Freios.
- Taxi.
- Pouso na agua.
- Derrapagem.
- Pista molhada.
- Grama, terra e neve futura.

## 6. Helicopteros

Helicopteros exigem tratamento proprio:

- Rotor principal.
- Rotor de cauda ou sistemas equivalentes.
- Torque.
- Translational lift.
- Autorotacao.
- Ground resonance futura.
- Coletivo, ciclico e pedais.

## 7. Planadores

Planadores devem suportar:

- Termicas.
- Onda orografica futura.
- Reboque futuro.
- Cabo/winch futuro.
- Energia total.
- Variometro realista.

## 8. Contratos de interface

### Entrada

- Estado de controles.
- Configuracao da aeronave.
- Massa e balanceamento.
- Estado atmosferico local.
- Estado da superficie.
- Estado de sistemas da aeronave.

### Saida

- Posicao, velocidade e aceleracao.
- Atitude e taxas angulares.
- Forcas e momentos.
- Estado aerodinamico.
- Eventos: estol, touchdown, overspeed, falha.
- Telemetria para replay e analise.

## 9. Validacao

Cada aeronave deve ter cenarios de teste:

- Decolagem.
- Subida.
- Cruzeiro.
- Curva padrao.
- Estol.
- Aproximacao.
- Pouso.
- Falha de motor quando aplicavel.
- Vento cruzado.
- Peso maximo e minimo.

## 10. Relacao com UE5

O Flight Dynamics Engine deve ser independente do UE5. UE5 recebe transformacoes, animacoes e efeitos por adapter. O core deve poder rodar em testes headless sem renderizacao.

# AeroWorld - AI Bible

A AI Bible define como a inteligencia artificial sera usada no AeroWorld de forma modular, segura, auditavel e util para simulacao, treinamento, criacao de conteudo e experiencia do jogador.

A IA deve ajudar o jogador a voar melhor, aprender mais rapido e viver um mundo mais convincente. Ela nao deve esconder erros de simulacao nem substituir sistemas deterministas quando regras claras forem mais adequadas.

- Instrutor.
- ATC.
- Passageiros.
- Mecanicos.
- Trafego aereo.
- Ajuda contextual.
- Gerador de missoes.

- Assistente de criadores.

|---|---|---|---|
| Regras deterministicas | Previsivel, testavel, barato | Menos flexivel | Usar em ATC basico, checklists e avaliacao |
| Behavior trees | Bom para agentes, facil de debugar | Pode ficar complexo em larga escala | Usar em trafego, passageiros e mecanicos |
| Utility AI | Boas escolhas dinamicas | Exige calibracao | Usar em trafego e mundo vivo |
| Modelos generativos em nuvem | Linguagem natural, explicacoes e missoes ricas | Custo, latencia, privacidade, dependencia online | Usar como camada opcional |
| Modelos locais | Funciona offline, privacidade melhor | Mais limitado e pesado no cliente | Avaliar por recurso |

**Status:** pendente de aprovacao por funcionalidade.

## 5. Arquitetura de IA

1. **AI Orchestrator:** coordena agentes e politicas.
2. **Context Builder:** transforma estado do jogo em contexto seguro.
3. **Agent Runtime:** executa agentes locais e regras.
4. **Cloud AI Gateway:** chama IA em nuvem quando aprovado.
5. **Safety Layer:** filtra comandos, privacidade e acoes perigosas.
6. **Action Adapter:** converte intencoes em comandos permitidos.
7. **Telemetry:** registra decisoes, falhas e qualidade.

## 6. IA que pode assumir controle

A IA pode assumir controle somente quando:

- O jogador solicitar explicitamente.
- O modo de assistencia permitir.
- A acao estiver dentro de limites seguros.
- O sistema registrar a transicao.
- O jogador puder retomar controle imediatamente.

## 7. IA offline e online

### Offline

- Checklists.
- Ajuda basica.
- Instrutor por regras.
- Copiloto simples.
- Trafego IA local.

### Online

- Dialogo natural.
- Geracao avancada de missoes.
- Explicacoes personalizadas.
- Moderacao.
- Analise de conteudo enviado.

## 8. Contratos com outros modulos

- **Flight Dynamics:** recebe limites e estados; nao deve ser manipulado de forma oculta.
- **Aircraft Systems:** permite executar checklists e comandos autorizados.
- **Mission Engine:** gera e avalia objetivos.
- **Career Engine:** ajusta progresso e recompensas por criterios verificaveis.
- **Networking:** sincroniza agentes relevantes.
- **Cloud Engine:** autentica e controla recursos online.

## 9. Regras de seguranca

- A IA nao deve executar compra, venda, publicacao ou submissao sem confirmacao.
- A IA nao deve alterar arquivos de criadores sem versao ou backup.
- A IA nao deve dar instrucao aeronautica real como substituta de formacao certificada.
- A IA deve diferenciar simulacao de aviacao real.
- Decisoes importantes devem ser auditaveis.

# AeroWorld - Multiplayer Architecture Document

## 1. Objetivo

O multiplayer do AeroWorld deve permitir mundo compartilhado, trafego de jogadores, eventos, ATC humano ou IA, empresas, missoes cooperativas futuras e modo hibrido sem comprometer simulacao local.

## 2. Principios

- Simulacao local continua sendo fluida.
- Rede replica o necessario, nao todos os detalhes internos.
- Tolerancia a latencia.
- Interpolacao visual.
- Separacao entre carreira, mundo online e sessao multiplayer.
- Moderacao e seguranca desde cedo.

## 3. Alternativas de arquitetura

| Alternativa | Vantagens | Desvantagens | Recomendacao |
|---|---|---|---|
| Peer-to-peer | Barato e simples | Fraude, NAT, seguranca, escala ruim | Nao recomendado |
| Servidor autoritativo total | Mais seguro | Custo alto, complexo para simulacao detalhada | Usar apenas onde necessario |
| Hibrido: cliente simula, servidor valida estado publico | Equilibra custo e experiencia | Exige anti-fraude e reconciliacao | Recomendado |
| Instancias dedicadas por regiao | Controle e estabilidade | Custo maior | Usar em eventos e regioes densas |

**Status:** pendente de aprovacao.

## 4. Estados replicados

- Posicao.
- Atitude.
- Velocidade.
- Luzes.
- Trem de pouso.
- Flaps visiveis.
- Identificacao.
- Plano de voo publico.
- Eventos relevantes.
- Estado de radio/ATC quando aplicavel.

## 5. Estados nao replicados integralmente

- Cada variavel interna de motor.
- Cada interruptor de cockpit.
- Calculos internos de flight dynamics.
- Dados privados de carreira.
- Informacoes sensiveis de conta.

## 6. Session model

- Mundo online persistente por regiao.
- Instancias por densidade.
- Eventos especiais.
- Sessao privada futura.
- Modo solo com dados online opcionais.

## 7. Trafego IA e jogadores

O Networking Engine deve coordenar:

- Jogadores reais.
- Trafego IA local.
- Trafego IA server-side futuro.
- ATC IA.
- Eventos do mundo.

Prioridade visual deve ser dada a aeronaves proximas e relevantes para seguranca.

## 8. Anti-fraude

- Validacao de velocidade e posicao.
- Validacao de conquistas.
- Separacao entre voo livre e carreira competitiva.
- Logs de eventos importantes.
- Deteccao de manipulacao de save.

## 9. Falhas de rede

Se a conexao cair:

1. O voo continua localmente.
2. Jogadores online desaparecem ou viram trafego estimado conforme regra futura.
3. Eventos de carreira entram na fila local.
4. Ao reconectar, estado publico e progresso sao reconciliados.

# AeroWorld - Core Design Document

## 1. Objetivo

O AeroWorld Core e o nucleo independente da plataforma. Ele deve conter os sistemas centrais de simulacao, dados, carreira, sincronizacao, IA, missao, conteudo e contratos de comunicacao. Mesmo usando UE5 como base visual/editorial, o Core deve continuar testavel sem UE5 e preparado para migracao futura.

## 2. Regra de fronteira

O AeroWorld Core nao deve depender diretamente de classes, assets ou ciclo de vida do UE5. A comunicacao com UE5 deve ocorrer por adapters.

```mermaid
flowchart LR
    UE5[UE5 Presentation Layer]
    Adapter[UE5 Adapter Layer]
    Core[AeroWorld Core]
    Cloud[Cloud Services]
    Tools[Creator Tools]

    UE5 <--> Adapter
    Adapter <--> Core
    Core <--> Cloud
    Tools <--> Core
```

## 3. Modulos centrais

| Modulo | Responsabilidade | Depende de | Exposto para |
|---|---|---|---|
| Core Runtime | ciclo de vida, jobs, tempo, eventos | Platform Abstraction | todos os modulos |
| Platform Abstraction | filesystem, threads, rede basica, relogio | sistema operacional | Core Runtime |
| Event Bus | comunicacao desacoplada | Core Runtime | todos os modulos |
| Data Model | entidades, ids, schemas, versoes | Serialization | todos os modulos |
| Serialization | leitura/escrita versionada | Platform Abstraction | Save, Cloud, SDK |
| Flight Dynamics | fisica de voo | Weather, Terrain, Aircraft Systems | UE5 Adapter, Telemetry |
| Aircraft Systems | eletrica, combustivel, hidraulica, falhas | Data Model | Flight Dynamics, Avionics |
| Avionics Core | instrumentos e navegacao | Aircraft Systems, World Data | UI, UE5 Adapter |
| World Data | aeroportos, terreno, tiles, geografia | Streaming, Digital Twin | Terrain, AI, Mission |
| Streaming Core | carregamento assincrono e cache | Platform, World Data | Terrain, UE5 Adapter |
| Weather Core | clima local e global | World Data | Flight Dynamics, Visual, Audio |
| Mission Core | objetivos, eventos e avaliacao | Career, World, AI | UI, Cloud |
| Career Core | progresso, empresas, licencas | Save, Cloud Sync | UI, Mission |
| Save Core | snapshots, event log, migrations | Serialization | Career, Cloud Sync |
| Cloud Sync Core | fila offline, conflitos, sync | Save, Cloud API | Career, Marketplace |
| AI Orchestration | agentes, contexto, politicas | Mission, Flight, Cloud AI | UI, Aircraft Systems |
| Networking Core | presenca, estado publico, sessoes | Cloud, Flight state | UE5 Adapter |
| Creator Validation | valida conteudo e manifestos | Data Model, SDK | Creator Tools, Marketplace |
| Plugin Runtime | carrega extensoes permitidas | Public API, Sandbox | Mod Engine |
| Public API Layer | contratos para criadores | Data Model | SDK, Plugins |
| Telemetry Core | metricas, logs e eventos | Core Runtime | Cloud, QA |

## 4. Fluxo geral de comunicacao

```mermaid
flowchart TD
    Input[Input Adapter] --> Runtime[Core Runtime]
    Runtime --> Flight[Flight Dynamics]
    Runtime --> Systems[Aircraft Systems]
    Runtime --> Weather[Weather Core]
    Runtime --> World[World Data]
    World --> Streaming[Streaming Core]
    Weather --> Flight
    Systems --> Flight
    Flight --> Events[Event Bus]
    Events --> Mission[Mission Core]
    Events --> Career[Career Core]
    Career --> Save[Save Core]
    Save --> Sync[Cloud Sync Core]
    Sync --> Cloud[Cloud API]
    Events --> AI[AI Orchestration]
    Flight --> Adapter[UE5 Adapter]
    World --> Adapter
    Weather --> Adapter
    Adapter --> UE5[UE5 Runtime]
```

## 5. Contratos por modulo

### 5.1 Core Runtime

**Responsabilidades**

- Inicializar e finalizar modulos.
- Controlar tick fixo e tick variavel.
- Gerenciar jobs.
- Controlar ordem de atualizacao.
- Publicar eventos de ciclo de vida.

**Interfaces**

- `ICoreModule`.
- `IJobSystem`.
- `ITimeSource`.
- `IModuleRegistry`.

**Contratos**

- Nenhum modulo pode assumir ordem de inicializacao sem declarar dependencia.
- Simulacao critica deve usar tick fixo.
- Modulos devem suportar shutdown limpo.

### 5.2 Event Bus

**Responsabilidades**

- Distribuir eventos entre modulos.
- Reduzir acoplamento direto.
- Registrar eventos para telemetria e replay quando marcado.

**Interfaces**

- `IEventPublisher`.
- `IEventSubscriber`.
- `IEventRecorder`.

**Contratos**

- Eventos publicos precisam de schema versionado.
- Eventos criticos devem ser idempotentes quando usados em sync.
- Eventos de alto volume devem usar canais especializados.

### 5.3 Flight Dynamics Engine

**Responsabilidades**

- Calcular forcas, momentos, estado de voo e eventos aerodinamicos.
- Receber clima, terreno, massa, controles e sistemas.
- Emitir estado de aeronave para visual, audio, replay e rede.

**Interfaces**

- `IFlightDynamicsModel`.
- `IAircraftStateProvider`.
- `IControlInputSink`.
- `IFlightTelemetrySource`.

**Dependencias**

- Weather Core.
- Terrain/World Data.
- Aircraft Systems.
- Core Runtime.

**Contratos**

- Nao depende de UE5.
- Deve rodar em teste headless.
- Deve ser deterministico em cenarios controlados.

### 5.4 Aircraft Systems

**Responsabilidades**

- Simular combustivel, eletrica, hidraulica, pressurizacao, trem de pouso, falhas e desgaste.
- Expor comandos autorizados para jogador, IA e plugins.

**Interfaces**

- `IAircraftSystemsModel`.
- `ISystemCommand`.
- `ISystemStatusProvider`.

**Contratos**

- Comandos devem validar permissao.
- Estados persistentes devem ser versionados.
- Falhas devem ser reproduziveis quando gravadas em replay.

### 5.5 Avionics Core

**Responsabilidades**

- Instrumentos analogicos e digitais.
- Navegacao.
- Radios.
- Autopilot.
- FMS/GPS futuro.

**Interfaces**

- `IInstrumentDataSource`.
- `INavigationProvider`.
- `IAutopilotController`.

**Contratos**

- UI pode variar, dados nao.
- Autopilot deve usar comandos oficiais de controle.
- Dados aeronauticos devem ter origem e versao.

### 5.6 World Data

**Responsabilidades**

- Representar dados do planeta, aeroportos, tiles, objetos, rios, estradas e metadados.
- Fornecer consultas espaciais.

**Interfaces**

- `IWorldQuery`.
- `IAirportRepository`.
- `ITileRepository`.
- `IGeoCoordinateService`.

**Contratos**

- Dados tem licenca e versao.
- Coordenadas devem seguir padrao unico.
- Consultas devem degradar quando dados nao estiverem carregados.

### 5.7 Streaming Core

**Responsabilidades**

- Priorizar carregamento.
- Gerenciar cache.
- Cancelar requisicoes obsoletas.
- Entregar dados para World, Terrain e UE5 Adapter.

**Interfaces**

- `IStreamingRequestQueue`.
- `ICacheStore`.
- `IAssetChunkProvider`.

**Contratos**

- Streaming nao pode bloquear tick de simulacao.
- Falha de rede deve retornar fallback.
- Cache deve respeitar versao de conteudo.

### 5.8 Weather Core

**Responsabilidades**

- Estado atmosferico local.
- Vento, turbulencia, visibilidade, chuva, gelo e termicas futuras.
- Integracao com fontes reais e presets offline.

**Interfaces**

- `IWeatherProvider`.
- `IAtmosphereSample`.
- `IWeatherTransition`.

**Contratos**

- Flight Dynamics recebe amostras fisicas, nao efeitos visuais.
- Visual recebe parametros renderizaveis por adapter.
- Dados reais precisam de timestamp e origem.

### 5.9 Mission Core

**Responsabilidades**

- Objetivos.
- Briefing e debriefing.
- Avaliacao.
- Recompensas.
- Eventos de missao.

**Interfaces**

- `IMissionDefinition`.
- `IMissionRuntime`.
- `IMissionEvaluator`.

**Contratos**

- Missoes devem ser serializaveis.
- Conteudo de criadores deve passar validacao.
- Recompensas de carreira precisam ser auditaveis.

### 5.10 Career Core

**Responsabilidades**

- Horas de voo.
- Licencas.
- Empresas.
- Reputacao.
- Contratos.
- Frota.
- Conquistas.

**Interfaces**

- `ICareerProfile`.
- `ICareerEventLog`.
- `IRewardService`.

**Contratos**

- Eventos de carreira devem ser idempotentes.
- Estado de carreira deve sincronizar com cloud.
- Dados sensiveis nao devem ser expostos a plugins sem permissao.

### 5.11 Save Core

**Responsabilidades**

- Save local.
- Snapshots.
- Event log.
- Migracoes.
- Recuperacao apos falha.

**Interfaces**

- `ISaveStore`.
- `IEventLogStore`.
- `IMigrationRunner`.

**Contratos**

- Saves devem ter versao.
- Escrita deve ser atomica.
- Corrupcao deve ter estrategia de recuperacao.

### 5.12 Cloud Sync Core

**Responsabilidades**

- Sincronizar estado local e cloud.
- Resolver conflitos.
- Trabalhar offline-first.
- Validar integridade.

**Interfaces**

- `ISyncQueue`.
- `IConflictResolver`.
- `ICloudClient`.

**Contratos**

- Reenvio deve ser seguro.
- Sync nao pode bloquear voo.
- Conflitos precisam ser rastreaveis.

### 5.13 AI Orchestration

**Responsabilidades**

- Coordenar copiloto, instrutor, ATC, trafego, passageiros e geracao de missoes.
- Aplicar politicas de seguranca.
- Converter contexto em acoes permitidas.

**Interfaces**

**Contratos**

### 5.14 Networking Core

**Responsabilidades**

### 5.15 Creator Validation

**Contratos**

- Validacao local e cloud devem compartilhar regras.
- Conteudo rejeitado deve explicar motivo.
- Conteudo aprovado deve ser assinado.

## 6. Fluxo de um frame de simulacao

1. Input Adapter coleta comandos.
2. Core Runtime avanca tick fixo.
3. Aircraft Systems atualiza estados.
4. Weather Core fornece amostra atmosferica.
5. World Data fornece terreno/superficie.
6. Flight Dynamics calcula novo estado.
7. Event Bus publica eventos relevantes.
8. Mission, Career, AI e Telemetry consomem eventos.
9. UE5 Adapter recebe estado visual.
10. Save/Cloud enfileiram eventos persistentes sem bloquear.

## 7. Fluxo de sync hibrido

```mermaid
sequenceDiagram
    participant Game as Game Client
    participant Save as Save Core
    participant Sync as Cloud Sync Core
    participant Cloud as Cloud Service

    Game->>Save: Record career event
    Save->>Sync: Queue event
    Sync-->>Game: Continue offline if needed
    Sync->>Cloud: Send pending events
    Cloud->>Cloud: Validate and apply
    Cloud-->>Sync: Confirm state version
    Sync->>Save: Mark events confirmed
```

## 8. Alternativas estruturais ainda pendentes

| Decisao | Alternativas | Recomendacao |
|---|---|---|
| Core language | C++, Rust, C# | C++ para runtime; Rust em servicos/ferramentas |
| IPC/adapters UE5 | C++ linkage, local RPC, shared memory | C++ linkage inicialmente |
| Event bus | Sync typed events, async queues, broker interno | Hibrido: typed events + filas por dominio |
| Plugin model | Data-only, sandbox script, native plugins | Data-only primeiro, scripts depois |
| Serialization | JSON, binary versionado, protobuf | Binary versionado para runtime; JSON para manifestos |

**Status:** todas pendentes de aprovacao antes de implementacao definitiva.

## 9. Regras de dependencia

- Core Runtime pode depender apenas de Platform Abstraction.
- Modulos de dominio nao podem depender de UE5.
- Cloud Sync depende de Save, mas Save nao depende de Cloud Sync.
- Flight Dynamics pode ler Weather e World, mas nao deve gravar neles.
- AI pode solicitar acoes, mas Action Gate decide se sao permitidas.
- Public API nao pode expor tipos internos instaveis.

## 10. Criterios de aceitacao do Core

- Compila e roda sem UE5.
- Executa teste headless de voo.
- Persiste e recarrega estado.
- Simula queda e retorno de internet.
- Emite telemetria.
- Permite adapter UE5 sem dependencia reversa.
- Possui contratos versionados.
- Possui ADRs para decisoes estruturais.

# AeroWorld - Coding Standards

## 1. Objective

Define coding conventions for future implementation without starting development in Phase 1.

## 2. Naming Conventions

- Types: `PascalCase`.
- Interfaces: `IName`.
- Functions: `camelCase` or project standard selected by ADR.
- Constants: `kName` or `UPPER_CASE` selected by module standard.
- Files: descriptive, module-scoped.

## 3. Folder Structure

```text
Source/
  Core/
  FlightDynamics/
  AircraftSystems/
  Weather/
  World/
  Save/
  CloudSync/
  AI/
  Networking/
  Plugins/
  PublicAPI/
  UE5Adapter/
Tests/
Tools/
Content/
```

## 4. Comments and Documentation

- Comments explain why, not obvious what.
- Public interfaces require documentation.
- Complex algorithms require references and test cases.
- ADRs document structural choices.

## 5. C++ Practices

- Prefer RAII.
- Avoid global mutable state.
- Separate allocation-heavy work from frame-critical paths.
- Use strong types for units.
- Keep deterministic simulation paths testable.
- Avoid direct UE5 dependency in Core modules.

## 6. Module Organization

- Each module owns its public interface.
- Dependencies must be explicit.
- No circular dependencies.
- Tests live near module or under `Tests/`.

## 7. Acceptance Criteria

- Future code follows module boundaries.
- Core compiles without UE5.
- Interfaces are versioned when public.
- Tests are required for simulation-critical code.

# AeroWorld - Architecture Overview

## Summary

AeroWorld uses a hybrid architecture:

- Unreal Engine 5 is recommended for presentation, editor tooling and visual runtime.
- AeroWorld Core remains independent and owns simulation, flight dynamics, save, career, AI orchestration, cloud sync, validation and public contracts.

## Core Boundary

```mermaid
flowchart LR
    UE5[UE5 Presentation]
    Adapter[UE5 Adapter]
    Core[AeroWorld Core]
    Cloud[Horizonte Cloud]

    UE5 <--> Adapter
    Adapter <--> Core
    Core <--> Cloud
```

## Key Rules

- Core must compile and run without UE5.
- Structural changes require ADR.
- Save must work offline.
- Cloud sync must not block flight.
- Creator content must pass validation.
- Marketplace packages must be signed.
